### EXPLAIN QUERY PLAN Analysis

**Baseline:** All queries use SCAN, ORDER BY uses TEMP B-TREE

**Strategy A (session_id):**
- Q1, Q2, Q5, Q6: SEARCH USING INDEX idx_obs_session
- Q3, Q4: still SCAN

**Strategy B (time):**
- Q2, Q3, Q4, Q5, Q6: SEARCH USING INDEX idx_obs_sampled_at
- Q1: still SCAN

**Strategy C (composite):**
- Q1, Q2, Q5, Q6: SEARCH USING INDEX idx_obs_session_time
- Q3, Q4: still SCAN
- Q6 is extremely fast (0.37ms) because index directly locates latest observation

## Recommendation

**Strategy C: `(session_id, timestamp)` composite index**

### Why

1. **Q6 (latest observation) is critical for real-time monitoring**: 19ms → 0.37ms (51x improvement)
2. **Q5 (session timeline) is the most common query pattern**: 27ms → 5.85ms (4.7x improvement)
3. **Q2 (time window within session) benefits significantly**: 26ms → 7.57ms (3.5x improvement)
4. **Covers 80% of Thalos access patterns**

### Write penalty is acceptable

- Insert throughput: 192K → 80K rows/s (60% reduction)
- Thalos workload: 20ch × 10Hz = 12K rows/min = 200 rows/s
- Even with penalty: 80K rows/s >> 200 rows/s required
- Thalos is read-heavy for observations

## Implementation

```sql
CREATE INDEX idx_obs_session_time ON observations(session_id, timestamp);
```
